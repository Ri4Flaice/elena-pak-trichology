# Отправка через GreenAPI с ограничением интенсивности

## Установка и обновление

1. Остановите отправку в старой версии приложения; не держите её запущенной параллельно с новой.
2. Сделайте резервную копию PostgreSQL и сначала проверьте миграцию на копии базы.
3. Выполните `npm ci`, `npm run db:migrate`, затем `npm run build`. В Vercel миграции выполняет существующая команда `npm run vercel-build`.
4. Добавьте `GREEN_API_WEBHOOK_URL="https://YOUR-DOMAIN/api/green-api/webhook"` и отдельный `GREEN_API_WEBHOOK_SECRET` длиной от 32 символов. Используйте случайный секрет, отличный от пароля и `SESSION_SECRET`; не добавляйте его в Git. Перезапустите приложение после изменения окружения.
5. Убедитесь, что этот URL доступен GreenAPI извне. Он защищён Bearer-секретом и не использует браузерную сессию. Внешняя защита хостинга, например Vercel Deployment Protection, не должна перехватывать запросы на этот маршрут. Не отключайте проверку секрета в приложении.
6. Откройте «Контроль отправки → Настройки инстанса и очередь → Применить настройки инстанса». Это отдельное действие: развёртывание кода само не вызывает GreenAPI и не отправляет сообщения.
7. После применения настроек отправка заблокирована на пять минут, чтобы не начать её до окончания перезапуска. Затем нажмите «Проверить GreenAPI» и проведите тест на своих номерах, включая команду СТОП. Очистка очереди и ручная проверка также блокируют параллельный запуск; при сбое операции блокировка сохраняется до 90 секунд.

Инстанс получает задержку очереди 15000 мс, `autoTyping: 2` (10 символов/сек), входящие сообщения, исходящие сообщения API и телефона, статусы доставки и изменения авторизации. Уведомления с телефона включены для совместимости с рекомендацией GreenAPI о статусах. Постоянный online и автоматическое прочтение выключены; режим LID и остальные настройки не меняются.

Если настройки задаются вручную, используйте `webhookUrlToken="Bearer <GREEN_API_WEBHOOK_SECRET>"`. Перед продолжением приложение сверяет URL, полный заголовок, задержку от 15000 мс и необходимые типы вебхуков через `GetSettings`. Секреты не возвращаются в браузер. Настройки с задержкой 0 не пройдут проверку.

## Существующие данные

Миграция сохраняет кампании и создаёт независимый журнал попыток для старых `ACCEPTED`, `ERROR`, `UNKNOWN`, `SENDING`. Старые `SENDING` становятся `UNKNOWN`. Исторические записи привязываются к текущему `GREEN_API_ID_INSTANCE` при первом обращении; это рассчитано на прежнюю архитектуру с одним инстансом. Не меняйте этот ID до первого запуска после миграции.

В старой схеме нет времени фактической отправки: для дневного учёта истории используется `updatedAt`, переведённый из UTC в `Asia/Qyzylorda`. Статусы доставки и согласия не выдумываются. Поэтому старые неподтверждённые отправки могут блокировать новые до проверки в «Журнале попыток и ручной проверке». Сначала показываются до 20 старейших неподтверждённых попыток; после проверки обновляйте список.

Неопределённый результат сам по себе не разрешает повтор. Администратор проверяет WhatsApp/журнал GreenAPI и очередь, затем указывает результат и основание (от 10 символов). Для результата «Не отправлено» сервер дополнительно требует пустую очередь GreenAPI. Такая попытка становится допустимой для ручного повтора; её прежнее место в дневном лимите сохраняется.

## Работа администратора

- Загрузите один Excel, подтвердите согласия с источником. Можно отмечать по одному клиенту или явно подтвердить согласия для всего файла; ранее отписавшиеся номера это действие не восстанавливает.
- В текущей версии отписка окончательна для рассылок: массового восстановления согласия поверх отказа нет.
- Клиенты без согласия, с отказом или некорректным номером не отправляются. Исходный список и причины пропуска остаются в кампании.
- Нажмите «Начать»/«Продолжить». Пока вкладка открыта, браузер запрашивает по одному сообщению, ожидая разрешённое сервером время. Нет фоновой отправки по cron.
- После серии и вне рабочего времени продолжение ручное. Перезагрузка, другая вкладка и новая кампания не сбрасывают общие ограничения.
- «Приостановить» запрещает новые отправки на сервере. Сообщение, запрос которого уже начат или принято провайдером, ещё может уйти.
- Из-за сбоя, недоступных вебхуков, ошибки провайдера или потери авторизации отправка останавливается. Успешная авторизация сама не возобновляет рассылку.
- СТОП / STOP / ОТПИСКА (без учёта регистра и пробелов по краям) исключают номер во всех кампаниях. Иные формулировки отказа отмечайте вручную в журнале клиента.
- Если СТОП пришёл с неизвестным `@lid`, отправка останавливается; привяжите телефон клиента в «Отписках с неизвестным телефоном». Отказ сохранится и для номера.
- Очистка очереди — отдельное подтверждаемое действие для всего инстанса. Оно не удаляет журнал попыток и не означает, что каждое сообщение точно не было отправлено.

## Хранение и проверки

`SenderState` — единый источник ограничений. Разрешение отправить, суточная квота, серия, согласие и блокировка проверяются в транзакции с блокировкой строки инстанса. HTTP-вызовы GreenAPI выполняются после фиксации резервирования, вне транзакции. Все зарезервированные попытки расходуют лимит, даже при ошибках. `SendAttempt` не удаляется каскадом с кампанией.

`GreenWebhookEvent` хранит минимальные нормализованные данные события, без текста переписки и файлов. Повторы идемпотентны; ранний статус сохраняется до появления `idMessage`; поздний `sent` не понижает `read`. Ошибки без `idMessage` не привязываются по одному телефону: это может ошибочно сопоставить старое сообщение, поэтому требуется ручная проверка. Уведомление `incomingBlock` не используется как сигнал жалоб.

Ограничения относятся к отправкам этого приложения. Для другого приложения или ручных массовых отправок на том же номере нет общего надёжного учёта; используйте единственный источник массовой отправки. Реакция получателей, согласие и история номера остаются важными: настройки не гарантируют отсутствие блокировки.

Проверки: `npm run test`, `npm run lint`, `npm run build`. Интеграционные тесты используют отдельную PGlite-базу в памяти, применяют SQL-миграции и выполняют реальные запросы Prisma; GreenAPI подменяется заглушкой. PGlite использует одно подключение, поэтому проверка реальной конкуренции блокировок между несколькими PostgreSQL-подключениями дополнительно нужна при проверке на копии рабочей базы. Тесты не отправляют реальные сообщения и не используют рабочую БД или инстанс.
